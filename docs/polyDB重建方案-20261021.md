# polyDB 重建方案：COD-Full / COD-Inorg（2026-10-21）

> 目标：**以 `D:\Project\XRD\PolyXRD-DataBase\COD` 的 COD CIF 为唯一数据源，从零重建两个外挂库**
> `COD-Full-<日期>.polyDB` 与 `COD-Inorg-<日期>.polyDB`，格式扩展名 **`.polyDB`**，可存放在任意文件夹、在 PolyXRD「外挂数据库管理」里指过去即用。
>
> 三条边界：① **不读、不转换任何旧 sqlite 库**；② **本次只用 COD**（PCOD / TCOD 暂不入库，ID 段预留）；③ 优先级 **准确性 > 检索速度 > 库体积**。
> 本文是**执行方案**：每个步骤都有输入 / 产出 / 命令 / 验收判据，可单独交付、单独验证。

## 1. 必须先定死的一件事：峰口径（关键风险，已实测确认）

反推旧库与现行构建脚本的口径**并不一致**，所以**不能**用"与旧库逐字段比对"当验收（会假阳性），必须由 13 试样基准定档：

| | 旧库 `COD_inorganics.sqlite`（实测 300 条） | 现行 `build_3cod.py` 定稿口径 |
|---|---|---|
| d 截止 | **无**（最小 d ≈0.771 Å ≈ λ/2） | **d ≥ 1.0 Å**（2θ 5–100.76°） |
| 每相峰数 | ≤**500**（d 降序截断） | ≤**100** |
| 存储精度 | d 4 位 / I 2 位小数 | 全精度 → 打包 f32 / u16 |
| λ、合并、归一 | 1.5406 Å、等价反射按 2θ 合并、I 归一 max=1000（同） | 同 |

前 3 条峰的 d 值两者逐条吻合（10.7438 / 9.5584 / 8.4480），说明物理模型一致、差异只在**截断范围与条数**。故设置 **S2 峰口径定档**：三候选各建迷你库、跑基准，选**不劣于旧库且体积最小**者。

## 2. 产物定义

| 项 | 定义 |
|---|---|
| 命名 | `COD-Full-<YYYYMMDD>.polyDB` / `COD-Inorg-<YYYYMMDD>.polyDB` |
| 形态 | **目录容器**（内部多文件，便于 mmap 与可选侧车）；分发可整体打包 zip，解压即用 |
| 存放 | 任意文件夹（D 盘、移动硬盘、NAS 均可），PolyXRD 外挂库管理指到该目录 |
| 内容（v1） | `meta.json`（版本/峰口径/构建信息/校验和）、`index.sqlite`（元数据 + 字符串表 + FTS5）、`peaks_d.f32`、`peaks_i.u16`、`bins.u8`（d 分箱位图倒排）、`elem.u8`（元素位图）、`sites.bin`+`sites_off.i64`（侧车）、可选 `cifs.tar.zst` |
| ID 规则 | **COD 原号**（1,000,000+）；用户自建库 ≥9 亿号段不动；PCOD/TCOD 预留 +20M / +100M 偏移（本期不用） |
| 检索结构 | 位图倒排生成候选（箱宽 0.05 Å，493 箱）→ ≤800 候选按行 mmap 取强峰 → Hanawalt 打分 → FOM |
| 定位 | **COD-Inorg（7.9 万相）= 默认交互库**（与原 7.1 万相内置库同量级，基线可比）；**COD-Full（53 万相）= 扩展库**（注意：库越大排序稀释越强，详见 §6 风险） |

## 6. 风险与不做清单

| 项 | 决定 | 理由 |
|---|---|---|
| 读旧 sqlite 做转换 | **不做** | 用户要求：以 CIF 为起点重建，不带历史包袱 |
| 本期入 PCOD / TCOD | **不做** | 只用 COD；ID 偏移段已预留，后续加库不改格式 |
| 改 Hanawalt / FoM 权重 | **不做** | 实测 5 项"直觉净负"；改了基准不可比 |
| 检索链路写库 | **禁止** | 一律 mmap 只读 / `connect_ro()` |
| 风险：COD-Full 排序稀释 | Full 定位为"扩展库"，默认交互用 Inorg | 实测库越大 top-1 越差（9/13 → 1/13）；53 万相仍有稀释，需在 S19 单独评估 Full 的基准表现 |
| 风险：峰口径变更 | S2 消融定档 | 已实测旧库与现行口径不同（§1） |
| 风险：CIF 解析失败 | 计入 skip 并分类 | 试产 60 条中 2 条失败（无位点/无体积），属预期 |
| 风险：mmap 在网络盘 / 32 位环境 | reader 提供 `preload` 回退 | 挂载时探测 |
| 109.59 GiB 源 CIF 的处理 | **不在本期**：仅只读扫描出清单 | 属 M6.2 的独立事项，用户确认后再动 |

### 8.2 三个必须记住的坑（本次实测踩到）

**① 预筛的"排序键"比"索引峰数"重要一个数量级。**
位图只用来**筛资格**（`counts>=min_match`，M=40 时是精确结果的超集）；
真正决定候选池的是**排序**。第一版按 `(counts, wsum)` 排序 —— 这是召回型
指标，偏爱峰多而密的物相，13 试样 top-100 漏检 24~100 条（最差 5-1 漏 96 条）。
改成按精确打分主键的**上界**（main_peak_match → top_precision → 加权召回）
分层后降到 0~2 条，再加自适应扩池归零。

**② 资格判据本身几乎没有选择性，别指望它过滤。**
25 个测量峰 × 40 条参考峰，凑 3 个命中太容易：实测 77,500 相里 98.6% 都通过
`n_matched_meas>=3`。所以"缩小候选池"的收益必须从排序里榨，不能靠加严判据
（加严 = 真丢物相）。

**③ 断点续跑的陈旧 part 会静默吞数据。**
首建 72,149 相却只报 1,345 条 skip，清单 79,198 差 5,704 条无账可查 —— 是
parts 目录里上一轮的 part 文件被当作"已完成"复用。现已加**条数守恒检查**
（输入 == 入库 + 跳过，不平即告警）与**skip 原因分类**，重建后 77,500 相全部
对账。此坑对 S11（Full，53 万相）风险更大，必须带 `--force` 跑首轮。

### 8.3 列表式多库挂载（S21–S24，v4.0.0 界面重设计）

**动机**：旧模型"一个类型一个槽位"（COD 无机物 / 全库索引 / PDF2 / XinMatch
各一行）在只有四类库、每类只挂一份的年代够用，但实际使用里立刻卡住 ——
手里既有 `COD-Inorg-20261021.polyDB` 又自己裁了无机子集、一份库在内置盘
一份在移动硬盘、同事导出给你的 polyDB 子集……这些都需要**同类型多份**共存。
所以界面改成一张表：**一行 = 一个已挂载的库，想挂几份挂几份，选中哪行就用
哪行检索**。

**模型**
```
Mount(id, kind, path, label, builtin, variant)
  kind ∈ {cod_inorganics, cod_index, pdf2, xinmatch, polydb, user}
  builtin=True  → 由旧配置槽位现算 (id 就是类型名), 不落盘、零迁移
  builtin=False → 用户自加, 落 ~/.polyxrd/db_mounts.json, id = <kind>:<路径摘要>
物相检索的 db_source = Mount.id  → resolve_mount() → (kind, path) → 引擎
```

**四个关键决定**

1. **内置项 id 直接取类型名**（`pdf2` / `cod_index` / `xinmatch` /
   `polydb:cod-inorg`）—— 历史代码与历史测试里的 `db_source="pdf2"` 一类字面量
   继续有效；`cod_full` / `polydb` / `polydb_full` 走别名表。
2. **挂载不再改配置槽位**。旧 `db_import.mount_databases` 是"每类覆盖配置"
   语义，同类型第二份库会把第一份顶掉（本次实测误伤过一次开发机配置）。
   新的 `db_mounts.mount_any` 只写挂载表，因此"同类型多份"才真正成立。
3. **引擎按显式路径只读打开**：`CIFDatabase(cod_db_path=…)` / `PDF2Database(path)`
   / `XinMatchDatabase(path)` / `PolyDatabase(path)`，`db_path=None` 时逐字沿用
   旧行为（按配置解析）。**打分与排序口径零改动** → 准确性不受影响，实测
   `1-2` 试样 `polydb` 与 `polydb:cod-inorg` top-5 逐条一致。
4. **「当前库」是显式动作**：管理界面「设为当前」写 `active` id；物相页下拉
   换源也会写回（两处必须始终一致）。选中行只改详情区，**不**自动换源 ——
   表格里点一下就换库、下一张谱跑出另一套结果太危险。

**边界（明确不支持）**
- 用户自建库（`user_phases.sqlite`）是单实例，位置由 `user_db` 自己管，
  列表里只展示、不给卸载（要清空请走用户库管理界面）。
- 一个数据库文件只能挂一次（同 `(kind, path)` 去重）；要"同一份库的两套过滤
  视图"应做成两份物理库，而不是两个挂载项。

**验收**：`test_db_mounts.py` 17 + `test_db_manager_dialog.py` 14 +
`test_pdf2_gui_source.py` 17 = 48 passed；相关模块回归子集 178 passed；
离屏冒烟（7 行列表、polyDB 77,500 相、行首「使用中」标记、PDF2 授权提示随
选中行显示/隐藏）全部通过。

### 8.4 口径定义（供 S11/S17 复用）

```
检索: d 由 2θ 换算(λ=1.5406)，取最强 25 峰，tolerance=0.02 Å 绝对容差
       min_match=3, max_ref_peaks=40, main_peak_topk=3, limit=100(prefilter)
打分: polyxrd.services.polydb._hanawalt_metric（与 cif_database 同口径）
排序: (main_peak_match, top_precision, intensity_weighted_top_recall,
       top_recall, meas_ratio, score) 降序，**并列按 row_idx 升序决胜**
      —— 与旧库稳定排序逐位一致，避免边界并列被误判成漏检
```
